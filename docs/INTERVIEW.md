# 项目一面试问答手册：法律智能问答系统

> 使用方法：先背「60 秒项目自述」和「数字速记卡」，再逐题吃透 15 个高频追问。
> 每题都标注了【追问】——面试官顺着你答案继续挖的问题，要能接住。

---

## 一、60 秒项目自述（开场必背）

> 这个项目是一个法律领域的智能问答系统，我担任技术负责人，负责整体架构设计和核心算法开发。
> 系统分三层：**意图识别层**用 bert-base-chinese 微调做 12 类法律咨询意图分类，测试集准确率 96.1%；
> **知识层**用 Neo4j 构建法律知识图谱，存了 20 个罪名、31 部法条和 30 条高频 FAQ，共 207 个节点；
> **对话层**是自研的多轮对话管理器，实现了槽位继承、指代消解、反问补全和置信度拒识。
> 后端用 Flask 提供 REST API，前端是 Web 聊天界面，整体有 25 个 pytest 测试用例保障质量，已开源。

## 三、15 个高频追问

### Q1. 为什么用 Bert 做意图识别，而不是 TF-IDF + SVM 或者规则？

**答**：三个原因。第一，法律意图之间语义很近，比如「罪名定义」和「构成要件」，词袋模型只看字面重合度分不开，而 Bert 预训练已经学过中文语义表示，微调后能捕捉这种细粒度差异。第二，用户问法千变万化，规则覆盖不全，Bert 泛化能力好。第三，数据量小（不到一千条）恰恰适合预训练模型迁移——从零训练词袋模型反而没有语义先验。
【追问】那为什么不用大模型 LLM 直接分类？→ 当时考虑了成本和可控性：LLM 调用有延迟和费用，本地小模型推理几十毫秒、零成本，而且分类结果确定性强，方便和后面的图谱检索流水线对接。当然现在迭代方向就是 LLM + RAG。

### Q2. 你的训练数据是怎么来的？为什么不用真实语料？

**答**：真实法律问答语料获取难、标注成本高，所以采用「**模板 × 实体槽位**」半自动构造：每个意图设计 15-30 种差异大的句型模板（疑问句/陈述句/口语/正式），实体槽（罪名、法条编号、金额）从领域词表随机采样填充，生成了近千条样本。词表覆盖 20 个常见罪名、15 部常用法条。
【追问】模板生成的数据会不会让模型只学会模板？→ 会，这是已知局限，所以模板设计时刻意拉开句型差异，并且评估时用**模板级切分**（见 Q3）保证测试集都是模型没见过的句型，分数是可信的。上线迭代方向是用真实用户问句做数据增强。

### Q3. 什么是「模板级防泄漏切分」？随机切分有什么问题？

**答**：因为数据是模板生成的，如果按句子随机切分，同一个模板生成的句子会同时出现在训练集和测试集——测试时模型相当于"见过原题"，准确率虚高，这就是**数据泄漏**。我的做法是：以模板为最小单元切分，同一个模板生成的所有句子只进一个集合，并且按类别分层、每类在 dev/test 至少保留 1 个模板。这样测试集的句型都是模型没见过的。
【追问】第一版就想到这个了吗？→ 没有，第一版就是按 (label, template) 随机切，导致测试集有的类只有 0-2 个样本、分布失衡，后来重构成模板级分层切分。这件事本身就是很好的面试素材。

### Q4. 96.1% 的准确率是怎么测出来的？可复现吗？

**答**：严格 train/dev/test 三分：训练只用 train，每轮在 dev 上评估、保存 dev 最优的 checkpoint，**test 只在训练全部结束后碰一次**。随机种子固定（42），数据处理、训练、评估脚本全部开源，评估报告（含混淆矩阵、per-class 指标）留在 docs/intent_report.md，任何人 clone 下来都能复现。
【追问】dev 和 test 差距大吗？→ dev 最优 98.99%，test 96.08%，差 3 个点左右，主要是 test 里 traffic_accident 等小样本类的波动，属于正常范围，没有明显过拟合。

### Q5. 训练过程中遇到过什么问题？怎么解决的？（必考）

**答**：印象深的有三个。第一，**多数类坍缩**：第一版训练完准确率 85% 但宏 F1 只有 0.26——模型把所有输入都预测成样本多的类。加了**类别加权损失**（权重 = 总数/（类别数×该类样本数））后宏 F1 升到 0.83。第二，**意图边界混淆**：「罪名定义」和「构成要件」互相全部分错，做了错误分析后发现是我自己模板设计有问题——「什么情况算盗窃罪」既像问定义又像问要件。重新划分意图边界：「是什么/意思/定义」归定义类，「构成/认定/要件/标准」归要件类，test acc 从 74.5% 提到 96.1%。第三，**机器没 GPU**：冻结 embedding + 前 8 层 encoder，只微调顶部 4 层 + 分类头，训练参数从 102M 降到 29M，CPU 上单轮 80 秒可接受，小数据下还更抗过拟合。
【追问】什么是错误分析（error analysis）？→ 就是把分错的样本拉出来按错误类型归类，找最大头的错误来源优先解决，而不是盲目加数据加轮数。

### Q6. 为什么冻结 Bert 底层？依据是什么？

**答**：两个依据。一是理论上：Bert 底层学的是通用语言特征（字词、句法），顶层才偏向任务特定语义，小数据场景下冻底层几乎不损失效果；二是工程上：我只有 CPU，冻结 8 层后训练参数从 102M 降到 29M，反向传播快了一倍多，而且可训练参数少、小数据下更不容易过拟合。实践中 dev 准确率也确实没受影响。
【追问】数据量大了怎么办？→ 数据到几万条时会考虑全量微调，甚至换用更大的领域预训练模型。

### Q7. 超参数（lr、batch、epoch）怎么定的？

**答**：参考了 BERT 原论文微调的推荐区间（lr 2e-5~5e-5，batch 16/32，epoch 2-4）做起点：lr 先用 2e-5 发现欠拟合（train loss 降不下去），调到 3e-5；batch 32 是 CPU 内存和速度的折中；epoch 通过 dev 曲线定的——观察到第 5 轮后 dev 开始波动下降（过拟合迹象），但总轮数设 8 是为了配合"保存 dev 最优 checkpoint"策略，多跑的轮数不会污染最终模型。warmup 10% 防止训练初期大梯度冲乱预训练权重。

### Q8. 知识图谱的 Schema 是怎么设计的？

**答**：核心是四类节点三类关系：罪名（Crime）带定义和量刑属性；法条（Article）带条文内容，通过 BELONGS_TO 指向法律（Law）；罪名的四要件拆成独立的 Element 节点，通过 HAS_ELEMENT 关联——这样「盗窃罪的构成要件」就是一次图遍历；罪名通过 DEFINED_IN 关联到法条，回答时能带上法律依据。另外民事类问题建模成 FAQ 节点挂到主题（Topic）节点下。所有写入用 MERGE 保证幂等，且先建唯一性约束防重复。
【追问】为什么四要件要拆成节点而不是存在罪名的属性里？→ 拆成节点后要件可以被多个罪名复用（比如多个罪的"主观方面"都涉及"非法占有目的"），未来可以按要件反查罪名，图的价值才体现出来；而且这是典型的"实体还是属性"建模决策——需要被独立查询/复用的就应该建模为节点。

### Q9. 为什么用 Neo4j 而不是 MySQL？

**答**：这个项目的查询模式是"关系遍历"——从罪名走到要件、走到法条，Cypher 写起来就是一句 `MATCH (c:Crime)-[:HAS_ELEMENT]->(e)`；用 MySQL 要多表 JOIN，关系一深就很别扭。而且 Neo4j 的图模型让领域知识结构可视化、可扩展，后面加"相似罪名""修正法案"这类关系时不用改表结构。当然如果业务是纯结构化查询，MySQL 更合适——选型要看查询模式。
【追问】Neo4j 怎么部署的？→ 本地 Neo4j Community + JDK 21，通过官方 Bolt 协议（7687 端口）用 Python driver 连接；也支持一键切到 AuraDB 云实例，连接信息全部走环境变量。

### Q10. 多轮对话是怎么实现的？

**答**：自研的对话管理器，三个核心机制。**槽位继承**：每个 session 维护槽位（比如当前罪名），用户说「那会判几年」没有实体时，自动继承上一轮的罪名。**指代消解**：检测到「它/这个罪」等指代词时映射到上下文槽位。**反问补全（槽位填充）**：识别出量刑意图但没有任何实体来源时，进入 pending 状态反问「您想咨询哪个罪名」，下一轮用户只答罪名也能完成查询。会话有 30 分钟 TTL，定期清理过期会话。
【追问】「它的构成要件呢」这种模型都不认识的输入怎么处理？→ 这就是 Q11 的兜底机制。

### Q11. 置信度拒识是怎么回事？阈值怎么定的？

**答**：模型 softmax 输出最大概率作为置信度，低于 0.5 就不强行回答，返回能力边界提示——宁拒勿错，法律场景尤其不能一本正经地胡说。阈值 0.5 是在 dev 上观察分布定的：正常查询置信度普遍 0.8+，OOD 输入大多低于 0.4，0.5 留了安全边际。但上线后发现一个真 bug：多轮场景里「那会判几年」这种短输入置信度天然偏低（0.40），被误杀了。修复方案是**上下文兜底**：有罪名槽位时，低置信度输入先按模型意图、再按关键词推断续聊意图（提到"要件"→要件查询、"判/刑"→量刑），结合上下文回答而不是机械拒识。这是拒识鲁棒性和多轮体验的平衡。
【追问】这个 bug 怎么发现的？→ 端到端验证脚本跑多轮用例时暴露的——所以我把这个脚本也留在了仓库里（tests/verify_e2e.py）。

### Q12. 实体识别为什么用词表匹配，不上 NER 模型？

**答**：罪名是封闭集合（刑法 400 多个罪名，项目收录 20 个常见罪名），词表 + 别名映射 + 按长度优先匹配就能做到接近 100% 的准确率，零成本零延迟。上 NER 模型（比如再微调一个 Bert-CRF）属于用高射炮打蚊子，还要再标一份序列标注数据。工程选型讲合适不讲高级。当然开放域实体（人名、公司名）就必须上 NER 了，那是迭代方向。

### Q13. Flask 后端怎么设计的？能扛并发吗？

**答**：REST 风格三个接口：POST /api/chat 对话、GET /api/health 健康检查（同时探活 Neo4j 和模型）、GET /api/stats 图谱统计。设计上模型和图谱连接都是**模块级单例**，避免每次请求重复加载几百 MB 权重；对话管理器无状态化（会话数据独立存储），为水平扩展留口。目前用的是 Flask 自带开发服务器，单进程；生产部署会换 waitress/gunicorn 多 worker，前置 Nginx 做反向代理和限流。会话现在存内存，多实例部署要切 Redis 集中存储。
【追问】接口怎么保证健壮性？→ 入参校验（空消息 400）、异常兜底（500 不暴露堆栈给前端）、健康检查区分模型/数据库两个维度。

### Q14. 测试怎么做的？

**答**：三层。单元测试 13 个：用 fake 的意图服务和图谱仓储做**依赖注入**，不依赖模型权重和数据库，专注测对话逻辑——槽位继承、指代消解、反问补全、会话隔离、拒识、法条归一化都覆盖了。模型冒烟测试 12 个：加载真实模型跑典型问句，断言意图和置信度。再加一个端到端脚本 verify_e2e.py：起真实服务模拟用户多轮对话全流程。对话管理器设计成构造函数注入依赖，就是为了可测性。

### Q15. 这个项目还有什么不足？让你继续做会怎么做？

**答**：坦诚说四点。第一，数据是模板构造的，和真实用户问法有差距——下一步接入真实问句做数据增强，模型定期重训；第二，民事类 FAQ 是关键词匹配，可以升级成语义检索（向量相似度），再往远走就是 **RAG**：图谱结构化检索 + LLM 生成式回答；第三，会话存内存，分布式部署要切 Redis；第四，没有容器化，下一步写 Dockerfile 和 docker-compose 一键拉起 Neo4j + 后端。这也是我为什么把每个模块都留了清晰接口的原因。

## 四、一类隐藏大题的答法：「你作为技术负责人做了什么？」

> 技术选型上：对比了 TF-IDF/Bert/LLM 三条意图识别路线，结合团队算力（无 GPU）和数据规模选定 Bert 微调；图数据库对比 Neo4j/NebulaGraph 后选了生态最成熟的 Neo4j。
> 任务拆解上：把系统拆成数据、模型、图谱、后端、前端五条线并行推进，定义好模块间接口（意图服务、图谱仓储都是接口注入）。
> 质量把控上：立了"评估先行"的规矩——先有测试集再谈模型效果，任何优化必须有指标提升才合入；累计解决 30+ 个问题，最典型的三类是多数类坍缩、意图边界混淆、低置信度误杀（见 Q5/Q11）。
> 交付上：开发文档、评估报告、部署手册、测试用例全部随代码入库。
